# codex-driven-coding

コーディング作業そのものは **codex に非対話モードで委譲**し、Claude（あなた＝オーケストレーター）は次の3点に専念する：

1. **作業指示の作成** — codex に渡す明確なプロンプト（何を・どこで・どの受け入れ条件で）を組み立てる
2. **成果物のレビュー** — codex が書いたコード（diff）と返答を検証する
3. **完了報告** — 問題がなければユーザーに作業完了を報告する

**核となる原則:** Claude はコードを自分で書かない。指示とレビューに徹し、Claude 枠（Anthropic 枠）を温存しながら codex（ChatGPT 枠）に実装を任せる。

## いつ使うか

- ファイルの新規作成・修正・リファクタ・バグ修正・テスト追加など、**実際にコードを書く作業**が発生するとき。
- ユーザーがコーディングタスクを依頼したとき（本スキルが既定の実装フロー）。

**使わない場合:**
- 調査・説明・軽微な1行修正など、委譲のオーバーヘッドが見合わないとき（Claude が直接処理してよい）。

**`codex:rescue` との違い:** `codex:rescue` は「1回投げて stdout をそのまま返す」フォワーダ型のサブエージェント。本スキルは Claude が能動的に指示を練り、diff を検品し、必要なら resume で反復する**オーケストレーション型**。

## フロー

### ① 作業指示を組み立てる

codex に渡すプロンプトには、少なくとも次を含める：

- **ゴール**: 何を達成したいか（1〜2文）
- **対象**: 触るべきファイル／モジュール（分かる範囲で。不明なら「まず調査してから」と指示）
- **制約**: 既存の規約・スタイル・使ってよい／いけないライブラリ、壊してはいけない挙動
- **受け入れ条件**: 完了の判定基準（例: 「`npm test` が通ること」「型エラーが出ないこと」）
- **報告要求**: 「変更したファイルと理由、実行したテストとその結果を最後に要約せよ」

曖昧な依頼は codex に渡す前に自分で具体化する。大きなタスクは1つの指示に詰め込まず、レビュー可能な単位に分割して順に委譲する。

### ② codex を非対話モードで呼ぶ

作業ディレクトリと受け入れ条件を固定した上で、次の形で呼ぶ（`SCRATCH` = セッションのスクラッチパッドディレクトリ）：

```bash
codex exec "<①で組み立てた作業指示>" \
  -c model_reasoning_effort="high" \
  --dangerously-bypass-approvals-and-sandbox \
  -C "<作業ディレクトリ（既定: リポジトリルート）>" \
  -o "$SCRATCH/codex-last-message.txt" \
  < /dev/null > "$SCRATCH/codex.log" 2>&1
```

**必須の作法:**

- **`< /dev/null`** — stdin をソケットのままにすると codex が起動前に永久ブロックすることがある。必ず `/dev/null` を繋ぐ。
- **`--dangerously-bypass-approvals-and-sandbox`** — 本環境（コンテナ）は外側でサンドボックス済みのため、codex にファイル編集を直接行わせる。
- **`-C <dir>`** — codex の作業ルート。既定はリポジトリルート。
- **`-o <file>`** — codex の最終メッセージ（要約）をファイルに書き出させ、レビュー時に読む。
- **`> "$SCRATCH/codex.log" 2>&1`** — 全出力をログへ退避。長くなるので端末に流さずファイルで受ける。

**モデル・effort:**
- `-c model_reasoning_effort="<none|minimal|low|medium|high|xhigh>"` … 重い実装ほど `high`。軽微な変更は `low`〜`medium`。
- モデルは既定（`~/.codex/config.toml`）に委ねる。特定モデルが必要なときだけ `--model "<name>"` を足す。ユーザー指定があればそれに従う。

呼び終えたら **ログから session id を控える**（`grep -i "session id" "$SCRATCH/codex.log"`）。反復修正のときに resume で使う。

### ③ 成果物をレビューする

codex の exit code とログ末尾、`-o` の最終メッセージを確認したうえで、**必ず実際の変更を自分の目で検証する**：

- `git status` / `git diff` で codex が触った範囲と内容を確認する。
- 受け入れ条件を Claude 自身が実行して確かめる（`npm test`、型チェック、lint、ビルド、対象スクリプトの実行など）。codex の「テストは通りました」を鵜呑みにせず自分で再現する。
- レビュー観点: ゴールを満たしているか／指示外の余計な変更をしていないか／既存の規約・スタイルに沿っているか／エラー処理・境界条件・明らかなバグはないか。

**判定:**
- **合格** → ④ 完了報告へ。
- **不合格 or 未完** → 具体的な指摘（どのファイルの何が・なぜダメか・期待する形）をまとめ、**同じ session を resume して修正を委譲**する：

  ```bash
  codex exec resume <SESSION_ID> "<指摘と修正指示>" \
    --dangerously-bypass-approvals-and-sandbox \
    -C "<作業ディレクトリ>" \
    -o "$SCRATCH/codex-last-message.txt" \
    < /dev/null > "$SCRATCH/codex.log" 2>&1
  ```

  session id が取れていなければ、文脈を含め直した新規プロンプトで ② から再実行する。修正は原則として**それを書いた codex に直させる**（Claude が手で直さない）。何度か反復しても収束しない・codex がレート上限で停滞する場合のみ、Claude が直接手を入れるフォールバックに切り替え、その旨を報告に明記する。

### ④ 完了報告

レビューに合格したら、ユーザーへ簡潔に報告する：

- **やったこと**: 変更内容の要約（1〜3行）
- **変更ファイル**: 主要な追加・修正ファイル（`file_path:line` 形式が望ましい）
- **検証結果**: 自分で実行した確認（テスト／lint／ビルド）とその結果を、通った・落ちたを含めありのままに
- **残課題**: あれば未対応事項・要判断事項

テストが落ちた・一部スキップした・Claude が直接手を入れた等は**隠さず正直に**書く。コミットやプッシュはユーザーが明示的に依頼した場合のみ行う。

## 注意

- 破壊的・不可逆な操作（大量削除・強制上書き・外部への送信）が絡むときは、委譲前にユーザーへ確認する。
- codex は `-C` で与えたディレクトリ配下を書き換える。想定外の場所を触っていないか ③ で必ず確認する。
